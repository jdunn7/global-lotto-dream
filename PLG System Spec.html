01Overview

PlayLottoGlobal is one product with four role-gated surfaces, not four separate apps. Every surface shares a single spine: one identity, one wallet, one theme, one data/service layer. A user moves between them based on who they are — never re-logging-in, never losing state.

AThe unified model

Think of it as concentric rings around a shared core. The core is the PLG_API service layer + session + wallet. Each surface is a view onto that core, gated by role.

  • Public Gateway & growth — anyone, no login. Splash, viral landing, live news. Funnels into sign-up.
  • Player The app — any signed-in player. Play, draws, wallet, tickets, rewards, profile.
  • Affiliate The network — players who opted into the affiliate program. Member Hub, portal, commission dashboard, viral tools.
  • Staff Back office — staff/board only. Marketing Hub (Hermes) and the Board & Admin CRM.
One rule that makes it unified: every button writes through PLG_API and every read comes from it. No screen invents its own state. Change a balance in checkout → the wallet popover, dashboard, and admin revenue all reflect it because they read the same store.

03Global systems

The shared spine. These five systems exist once and every screen consumes them — this is what makes the suite "one system" rather than a folder of pages.

1Navigation spine

  • Top bar (player app): logo → home, primary nav (Home · Games · Results · News · Rewards), wallet popover, notifications, profile-menu avatar.
  • Profile menu is the cross-surface launcher — Profile, Wallet, Refer & earn, Billing, Member Hub ↗, Affiliate dashboard ↗, Marketing hub ↗ (staff), Admin ↗ (staff), theme toggle, sign out.
  • Sidebar (all back-office surfaces): identical dock component — resizable, dockable left/right/bottom, persists per page (sidebar-dock.js).
  • Bottom nav (mobile, player app): Home · Games · Tickets · Rewards · Profile.
Rule: the logo always returns to that surface's home; the profile avatar always opens the cross-surface menu. Consistent everywhere.

2Auth & session

  • One session object: { authed, role, profile }. Set by auth.login / auth.signup, cleared by auth.logout.
  • Guests can browse public surfaces. Hitting a gated action (buy, withdraw, view portal) routes to Sign In, then returns to the intended screen.
  • "Browse as guest" exists on the auth screen; the app boots into a logged-in demo state for review.
  • Role lives on the session — the nav and route guards read session.role to show/hide affiliate & staff entries.

3Theme — dark / light fixed

One theme key drives the entire suite. Single source of truth: localStorage["lg_mode"] = "dark" | "light".

  • Toggling sets the key and adds/removes html.light. Every page reads the key on load, so the choice carries across all surfaces.
  • Light overrides live in extra.css (app) + per-surface html.light blocks (dashboard, marketing, portal, admin).
  • The fix: structural chrome (sidebars, top bars, nav controls, tables, tree nodes) was hardcoding dark hsl() values, so it stayed dark while cards flipped. Those now have html.light retints — no more split appearance.
Builder rule going forward: never hardcode a surface color. Use the semantic tokens (--bg, --bg-card, --border, --fg…). Tokens flip automatically; raw hsl() does not. Every new dark value needs a matching html.light override.

4Wallet & money

  • One wallet object: { playable, winnings, commission }. Shown in the header popover, the Wallet page, the dashboard, and (aggregated) admin revenue.
  • Writes: wallet.topUp, wallet.withdraw, payments.checkout, payouts.request. Each emits an event so every open view updates live.
  • Payment methods: cards (live brand detection + Luhn) via payments.addCard; crypto via payments.connectWallet (MetaMask, Coinbase, WalletConnect, Phantom, Trust, Rainbow).

5Service layer — the unifier

plg-api.js exposes one namespaced API. Today it resolves against a localStorage mock; flip PLG_API.config.mode = "live" + set baseUrl and every call becomes a real REST request — no UI changes.

  • auth.* — signup, login, session, reset
  • players.* — profile, stats, bank details
  • wallet.* — balance, topUp, withdraw
  • payments.* — cards, crypto, checkout
  • tickets.* — games, buy, results, draws
  • affiliate.* — network, commissions, waitlist, invite
  • payouts.* — request, list, stats
  • marketing.* — campaigns, Hermes send, AI generate
  • support.* — tickets, FAQs
  • admin.* — KPIs, P&L, risks, cap table…
Wire-to-backend checklist: 1) host the REST API matching the documented routes, 2) set baseUrl + mode:"live", 3) pass the bearer token from auth.login. The UI is already done.

05Build spec prompt

Unified Build Brief — PlayLottoGlobalcopy ↓
# PRODUCT
Build PlayLottoGlobal: one product, four role-gated surfaces sharing a
single spine. NOT four apps — one identity, one wallet, one theme, one
data layer. Users move between surfaces by role without re-auth.

# SURFACES & ROLES (additive)
- Public  (visitor): Gateway, Viral landing, Live news, Results
- Player  (signed in): app — play, draws, wallet, tickets, rewards, billing, profile
- Affiliate (opted in): Member Hub, Portal, Commission dashboard, Viral tools
- Staff   (granted): Marketing Hub (Hermes), Board/Admin CRM
Access is additive; nav reveals more entries as role grows.

# THE SPINE (build these once, every screen consumes them)
1. Service layer `PLG_API`: one namespaced async API
   (auth, players, wallet, payments, tickets, affiliate, payouts,
    marketing, support, admin). Mock-backed via localStorage today;
   flip `config.mode="live"` + `baseUrl` → real REST, zero UI change.
   EVERY button writes through it; EVERY read comes from it.
2. Session: { authed, role, profile }. Guests browse public; a gated
   action routes to Sign In then returns. Nav reads session.role.
3. Wallet: { playable, winnings, commission } shown in header popover,
   Wallet page, dashboard, admin. Writes emit events; open views live-update.
4. Theme: ONE key `localStorage["lg_mode"]` = dark|light. Toggle adds
   `html.light`. Read on load so choice carries across ALL surfaces.
5. Nav: logo→home; avatar→cross-surface profile menu; back-office
   sidebar is one dockable/resizable component, persisted per page.

# DESIGN SYSTEM (binding)
- Triple Seven tokens: Outfit (display) + Inter (body); emerald primary;
  PLG brand = navy/indigo + muted gold. Restrained, executive — never rainbow.
- NEVER hardcode a surface color. Use semantic tokens
  (--bg, --bg-card, --border, --fg, --fg-muted…). Tokens flip with theme;
  raw hsl() does not. Any dark value MUST ship a matching `html.light` override.
- Radii 10/16/24/30px; soft 1px borders; gentle ease-out motion (200/300/500ms).
- Icons: white stroke + dark outline; no emoji in chrome.

# WIRING RULES
- Pick Numbers → Checkout → Confirmation → Live Draw is the buy spine;
  Checkout calls payments.checkout + tickets.buyTicket, which move the wallet.
- Every CTA resolves to a real route or PLG_API call — no dead buttons.
- Rewards "Become affiliate" grants the affiliate role and reveals its nav.
- Staff surfaces gate on session.role === "staff".

# DELIVER
A single coherent build where any state change (a purchase, a payout, a
new signup) propagates everywhere because all screens read one store.
How to use: hand this spec + the existing files to the builder. It already matches what's built — use it to keep new work consistent, to onboard a developer, or to brief the backend team on the exact PLG_API contract to implement.
